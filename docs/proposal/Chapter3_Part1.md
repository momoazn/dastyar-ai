# فصل سوم: روش تحقیق و مراحل اجرا

## ۳-۱ مقدمه

فصل سوم به تشریح متدولوژی پژوهش، معماری فنی سیستم و جزئیات پیاده‌سازی اجزای مختلف «دستیار هوشمند» اختصاص دارد. با توجه به اینکه ماهیت این پژوهش «توسعه‌ای-کاربردی» (Applied-Developmental) است، تمرکز اصلی بر روی فرآیند مهندسی نرم‌افزار، انتخاب ابزارها، طراحی الگوهای معماری و نحوه یکپارچه‌سازی ماژول‌های هوش مصنوعی خواهد بود. در این فصل، نقشه راه دقیقی از «چگونگی» ساخت سیستم ارائه می‌شود که از تحلیل نیازمندی‌ها آغاز شده و به طراحی پایگاه داده، پیاده‌سازی سرویس‌ها و در نهایت روش‌های آزمون و ارزیابی ختم می‌گردد.

## ۳-۲ روش پژوهش

روش انجام این پژوهش مبتنی بر **«متدولوژی چابک» (Agile Methodology)** با رویکرد تکرارپذیر (Iterative) است. فرآیند توسعه به چرخه‌های کوتاه (Sprints) تقسیم می‌شود که در هر چرخه، بخشی از قابلیت‌های سیستم پیاده‌سازی، تست و ارزیابی می‌گردد.

مراحل اصلی اجرا عبارتند از:

1.  **تحلیل و امکان‌سنجی:** بررسی مدل‌های موجود و انتخاب پشته تکنولوژی (انجام شده در فصول ۱ و ۲).
2.  **طراحی معماری (Architectural Design):** تعیین ساختار میکروسرویس‌ها و قراردادهای ارتباطی (API Contracts).
3.  **پیاده‌سازی هسته (Core Implementation):** توسعه موتورهای پردازشی سمت سرور.
4.  **توسعه رابط کاربری (UI/UX Development):** ساخت اینترفیس تعاملی برای کاربر نهایی.
5.  **یکپارچه‌سازی و تست (Integration & Testing):** اتصال ماژول‌ها و ارزیابی عملکرد کلی.

## ۳-۳ معماری کلان سیستم (High-Level Architecture)

معماری پیشنهادی برای این سیستم، یک معماری **«میکروسرویس ماژولار» (Modular Microservices)** است که تمام اجزای آن بر روی یک میزبان واحد (Localhost) مستقر می‌شوند. اگرچه میکروسرویس‌ها معمولاً برای سیستم‌های توزیع‌شده استفاده می‌شوند، اما استفاده از این الگو در مقیاس محلی به ما اجازه می‌دهد تا:

1.  فناوری‌های ناهمگون (Go برای Whisper، TypeScript برای منطق تجاری) را ترکیب کنیم.
2.  سربار پردازشی هر ماژول را ایزوله کنیم (Crash شدن سرویس صوت، کل برنامه را متوقف نمی‌کند).
3.  قابلیت مقیاس‌پذیری آینده (مثلاً انتقال سرویس‌های سنگین به سرور دیگر) را حفظ کنیم.

دیاگرام مفهومی معماری شامل سه لایه اصلی است:

- **لایه نمایش (Presentation Layer):** اپلیکیشن وب React که در مرورگر اجرا می‌شود.
- **لایه منطق تجاری (Business Logic Layer):** سرور اصلی (Main Server) مبتنی بر Bun و Hono که وظیفه مدیریت کاربران، دیتابیس و هماهنگی درخواست‌ها را دارد.
- **لایه محاسباتی (Compute Layer):** سرویس‌های تخصصی هوش مصنوعی (Whisper Service, LLM Service) که محاسبات سنگین تانسوری را انجام می‌دهند.

## ۳-۴ طراحی و پیاده‌سازی بخش سرور (Backend)

قلب تپنده سیستم، سرور مرکزی است که با استفاده از ران‌تایم **Bun** و فریم‌ورک **Hono** توسعه می‌یابد.

### ۳-۴-۱ چرا Hono؟

فریم‌ورک Hono (به معنی «شعله» در زبان ژاپنی) به دلیل استانداردهای مدرن وب (Web Standards) انتخاب شده است. برخلاف Express.js که وابسته به APIهای خاص Node.js است، Hono بر روی هر ران‌تایمی (Bun, Node, Deno, Cloudflare Workers) اجرا می‌شود. این ویژگی، پرتابل بودن کد را تضمین می‌کند. همچنین بنچ‌مارک‌ها نشان می‌دهند که Hono در پردازش درخواست‌های متنی (JSON Parsing) تا ۵ برابر سریع‌تر از Express عمل می‌کند.

### ۳-۴-۲ ایمنی نوع (Type Safety) با ORPC

یکی از بزرگترین چالش‌های توسعه وب، ناهماهنگی بین کدهای سرور و کلاینت است. برای حل این مشکل، ما از کتابخانه **ORPC (OpenRPC)** استفاده می‌کنیم.
در این روش، تمام ورودی‌ها و خروجی‌های API با استفاده از کتابخانه اعتبارسنجی **Zod** تعریف می‌شوند. این تعاریف (Schemas) به صورت خودکار تایپ‌های TypeScript را تولید می‌کنند که در سمت کلاینت استفاده می‌شود.

- **نتیجه:** اگر فیلدی در پاسخ سرور تغییر کند، کامپایلر در سمت کلاینت بلافاصله خطا می‌دهد (End-to-End Type Safety). این رویکرد باگ‌های زمان اجرا را به شدت کاهش می‌دهد.

### ۳-۴-۳ ساختار پایگاه داده (Database Schema)

پایگاه داده سیستم بر اساس مدل رابطه‌ای (Relational) طراحی شده و توسط **SQLite** مدیریت می‌شود. شمای دیتابیس شامل جداول کلیدی زیر است:

1.  **Users:** اطلاعات کاربران (برای نسخه چندکاربره احتمالی).
2.  **Threads:** نگهداری تاریخچه مکالمات. هر Thread یک Session گفتگو است.
3.  **Messages:** پیام‌های رد و بدل شده در هر Thread. هر پیام شامل فیلدهای `role` (کاربر/دستیار)، `content` و `metadata` (برای ذخیره اطلاعات توکن‌های مصرفی) است.
4.  **Documents:** متادیتای فایل‌های آپلود شده (نام، نوع، حجم، تاریخ آپلود).
5.  **Embeddings:** این جدول برای سیستم RAG حیاتی است. در این جدول، بردارهای عددی متناظر با هر قطعه متن (Text Chunk) ذخیره می‌شوند تا برای جستجوی شباهت مورد استفاده قرار گیرند.

برای مدیریت این جداول، از **Drizzle ORM** استفاده می‌کنیم. فایل پیکربندی `schema.ts` به عنوان منبع حقیقت (Source of Truth) عمل می‌کند و تمامی تغییرات دیتابیس (Migrations) از روی آن تولید می‌شوند.

### ۳-۴-۴ سیستم صف و مدیریت وظایف (Task Queue)

پردازش‌های هوش مصنوعی زمان‌بر هستند (مثلاً تولید یک تصویر ممکن است ۱۰ ثانیه طول بکشد). برای جلوگیری از مسدود شدن (Blocking) سرور اصلی، یک سیستم صف داخلی پیاده‌سازی می‌شود.

- درخواست‌های سنگین (مانند `transcribe_audio` یا `generate_image`) وارد یک صف حافظه (In-Memory Queue) می‌شوند.
- یک Worker جداگانه درخواست‌ها را یکی‌یکی از صف برداشته و به سرویس‌های هوش مصنوعی ارسال می‌کند.
- وضعیت پردازش از طریق WebSocket یا Server-Sent Events (SSE) به صورت بلادرنگ به کاربر گزارش می‌شود.

## ۳-۵ تحلیل عمیق معماری سرویس Whisper (Whisper Microservice Deep Dive)

سرویس تبدیل گفتار به متن، یکی از حساس‌ترین اجزای سیستم از نظر کارایی است. این سرویس به عنوان یک پروسه مستقل با زبان **Go** پیاده‌سازی شده است. انتخاب این پشته تکنولوژی (Tech Stack) تصادفی نبوده و حاصل بررسی دقیق نیازمندی‌های پردازشی است.

### ۳-۵-۱ پشته فناوری: چرا ترکیب Go و C++؟

- **هسته پردازشی (C++):** ما از کتابخانه `whisper.cpp` استفاده می‌کنیم که بازنویسی خالص C/C++ از مدل اصلی OpenAI است. این کتابخانه با حذف وابستگی به PyTorch و استفاده از دستورات برداری (AVX2/NEON)، سرعت استنتاج را روی CPU تا ۴ برابر افزایش می‌دهد.
- **لایه سرویس (Go):** زبان Go به دلیل مدیریت عالی همروندی (Goroutines) و سادگی در ایجاد وب‌سرور، به عنوان "چسب" (Glue) انتخاب شده است. این لایه وظیفه مدیریت درخواست‌های HTTP، صف‌بندی و پیش‌پردازش صدا را بر عهده دارد.
- **پل ارتباطی (CGO):** ارتباط بین Go و C++ از طریق مکانیسم **CGO** برقرار می‌شود. پکیج `bindings/go` توابع C را به صورت توابع native در Go در دسترس قرار می‌دهد. این روش سربار (Overhead) فراخوانی‌های سیستمی را حذف می‌کند (Zero-cost abstraction).

### ۳-۵-۲ خط لوله پردازش صدا (Audio Processing Pipeline)

مدل Whisper ورودی بسیار سخت‌گیرانه‌ای دارد: فایل WAV با نرخ نمونه‌برداری ۱۶ کیلوهرتز و تک‌کاناله (Mono). برای اینکه کاربر بتواند هر فرمتی (MP3, OGG, M4A) را آپلود کند، یک خط لوله پیش‌پردازش طراحی شده است:

1.  **تشخیص باینری FFmpeg:** سرویس ابتدا به دنبال فایل اجرایی `ffmpeg` در کنار خود می‌گردد. این طراحی "Portable" به ما اجازه می‌دهد تا باینری FFmpeg را همراه با برنامه توزیع کنیم و نیازی به نصب جداگانه توسط کاربر نباشد.
2.  **تبدیل فرمت:** هر فایل ورودی با دستور زیر نرمال‌سازی می‌شود:
    ```bash
    ffmpeg -i input_file -ar 16000 -ac 1 -loglevel error output.wav
    ```
3.  **دکودینگ PCM:** فایل WAV حاصله بایت به بایت خوانده شده و هدرهای RIFF/WAVE اعتبارسنجی می‌شوند. سپس داده‌های صوتی به آرایه‌ای از اعداد اعشاری (Float32) تبدیل شده و آماده تزریق به مدل می‌شوند.

### ۳-۵-۳ مدیریت مدل و همروندی (Model & Context Management)

یکی از چالش‌های اجرای مدل‌های هوش مصنوعی، مدیریت حافظه است. بارگذاری مدل در رم زمان‌بر است.

- **Model Caching:** سرویس از یک `Map` ایمن (Thread-safe) برای نگهداری مدل‌های بارگذاری شده استفاده می‌کند. مدل تنها یک بار از دیسک خوانده می‌شود (`whisper.New`).
- **Context Isolation:** برای هر درخواست تبدیل صدا، یک «زمینه پردازشی» (`NewContext`) جدید از روی مدل اصلی ساخته می‌شود. این طراحی هوشمندانه اجازه می‌دهد که:
  1.  چندین کاربر همزمان از یک مدل استفاده کنند (Parallel Inference).
  2.  حافظه مدل (Weights) بین درخواست‌ها اشتراک‌گذاری شود (Shared Memory).
  3.  وضعیت هر درخواست (مانند زبان انتخاب شده یا دمای مدل) ایزوله بماند.

### ۳-۵-۴ سازگاری با OpenAI API

این سرویس به گونه‌ای طراحی شده که دقیقاً شبیه به API شرکت OpenAI رفتار کند.

- مسیر `/v1/audio/transcriptions`: برای تبدیل صدا.
- مسیر `/v1/models`: برای لیست کردن مدل‌های موجود.
  این ویژگی به توسعه‌دهندگان Frontend اجازه می‌دهد تا بدون تغییر کد، بین سرویس ابری OpenAI و سرویس محلی ما سوئیچ کنند (Drop-in Replacement).
